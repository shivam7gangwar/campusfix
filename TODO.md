# CampusFix — Outcome checklist

Acceptance clauses below preserve the PRD’s required actors, behaviors, fields, transitions, exceptions, and post-launch targets. “Complete” means the feature is implemented and the listed checks have evidence; it does not mean unmeasured launch goals have been achieved.

- [x] **Authentication, campus roles, privacy, and administration:** Students, Staff, Authorities/Wardens, and Admins have role-appropriate access and actions. Login uses the approved Manus OAuth default because the PRD leaves college SSO/email-password/OTP choice open; new users default to Student and the app does not provide an insecure client-side role switch. The configured project owner becomes the initial Admin. Admins can manage signed-in users’ roles, categories/weights, active campus locations (blocks/buildings, floors, rooms/areas), location-scoped Authority assignments, visibility defaults, and SLA targets. Reporter identity is visible only to authorized roles. Anonymous/sensitive reports are restricted from public viewers and other campus roles; the submitting student can track their own report and Admins can inspect it. Campus-specific domain, authority-routing rules, and official SLA values remain configurable rather than invented.
- [x] **Student issue submission, uploads, duplicate suggestions, and priority:** The report form requires a short title and description; offers Electrical, Plumbing/Water, Wi-Fi/Network, Furniture/Equipment, Sanitation, Hostel, and Other; cascades location from Block/Building → Floor → Room/Area; accepts 1–3 images with size validation and client-side compression; captures self-reported Low/Medium/High urgency and a safety-hazard flag. Category is suggested from description keywords and remains editable. The server validates that a selected room/area is beneath an active floor and block. Before a public report is uploaded/submitted, matching checks open public issues at the same location/category and title/description similarity, then shows “Similar issues already reported” so the student can upvote/mark “I’m affected too” or submit anyway as a child report linked to the master. Restricted/anonymous reports are not exposed to public duplicate matching. The master’s report count reflects linked reports; distinct affected-student votes are counted separately and both feed priority. Priority Low/Medium/High/Critical is computed using category weight, safety hazard, duplicate reports/upvotes, and unresolved age; an Authority can override it. Matching only suggests; it never automatically merges. Authorized Authorities can manually merge/unmerge only open, public, non-anonymous issues; restricted and anonymous reports remain separate to prevent privacy leaks. Submission writes issue, report, upload association, activity, notification, and priority in a database transaction; image bytes, MIME signatures, ownership tokens, size, and usage are validated.
- [x] **Issue lifecycle, ownership, history, and in-app notifications:** Support Submitted → Under Review → Assigned → In Progress → Resolved → Closed, plus Reopened and Rejected with a reason. Every status change is timestamped and logged in an activity timeline. Students receive in-app notifications on each status change; maintain in-app events for submission, assignment, status change, and resolution. A student can confirm resolution or reopen within the campus-configured window (Admin setting: 1–30 days, default seven days). Authorized staff and authorities add notes/comments and progress updates. SLA due dates and overdue/breach indicators use editable priority targets. Staff/Authority reopening clears the old resolved timestamp so resolution analytics use the latest resolution.
- [x] **Student dashboard and public campus feed:** “My Issues” shows each reporter’s issues with current status and a path to issue detail. “Campus Issues” is a public student feed with filters and upvotes. Students can see status transparently, view public issue details, support matching reports without re-reporting, confirm resolution, and reopen an issue within the allowed window. Common reports can be public while reporter identity stays hidden; restricted/anonymous issues expose identity/details only to authorized roles. Student-facing pages are mobile-first and make the basic report flow achievable in under 60 seconds as the PRD’s success target; no elapsed-time result is claimed without measurement.
- [x] **Authority operations dashboard:** Authorities can view issues for their assigned area and descendants in list and Kanban views, sorted by priority, and filter by status, category, location, priority, date, and assignee. Provide search, sort, and bulk assign/status-change actions. The issue detail view includes photos, description, linked duplicates, comments, timeline, assignment controls, and due date. Authorities can assign an issue to a staff member, set a due date, and change category, priority, and status; they can manually merge/unmerge duplicate issues and add comments. Admin remains campus-wide; Authority access and sensitive actions are checked on the server.
- [x] **Staff task workflow:** Staff members have a view of their assigned issues with clear location, description, photos, and current status. Staff can update progress/status with notes and attach an “after” photo when work is complete; authorized issue readers see the attachment in the activity timeline.
- [x] **Admin/authority analytics and recurring hotspots:** Provide open-versus-resolved issues over time; average resolution time by category and location; a block/area hotspot view; top recurring issue types and repeated issues at the same location; overdue/unresolved issue lists; staff workload overview; and basic status/category/location counts. Show synthetic campus examples as sample data rather than real institutional facts; none is inserted into the shared database by default. Preserve the PRD’s post-launch success targets—at least 30% of reports linked to existing issues, first response/assignment under 24 hours, decreasing month-over-month resolution time, post-resolution satisfaction at least 4/5, and more than 80% of issues reported through the platform rather than WhatsApp—but do not present them as achieved; the empty Preview has no cohort evidence.
- [x] **Mobile-first interface, access controls, and MVP boundaries:** The UI is responsive; inputs are labeled, keyboard reachable, and have visible focus treatment. Validate user inputs and upload types/signatures; use owner-bound opaque upload tokens, role-and-assignee-aware detail access, Authority-area checks, private-by-default anonymous reports, short-lived signed photo URLs only after verifying the upload owner and issue/report association, and transactional database writes for issue submission. The live Preview and `/api/health` use HTTPS/healthy responses. No native mobile app, payments, inventory/vendor management, external ticketing/ERP integration, or fully automated AI issue resolution. Image-based duplicate detection, PWA/offline drafts, WhatsApp/Telegram bots, email delivery, SLA escalation, and predictive maintenance are not claimed as live without their providers/configuration. Code validation completed with TypeScript, 25 unit tests, production build, additive database migration/safe default seed, live health, and HTTP 200 route-manifest checks.
- [ ] **Campus-specific setup before real reports:** A project operator must sign in as the configured initial Admin, add the real active Block → Floor → Room/Area hierarchy, set the campus-approved visibility/SLA defaults, and assign Authority scopes and Staff roles. The PRD did not supply campus names, real locations, routing rules, an email domain, or official SLA values; the safe seed intentionally adds only default categories and starter SLA targets, not invented locations or issues. Until locations are configured, the report flow remains disabled and the Preview cannot accept a real campus report.
- [ ] **Email notifications and SLA escalation:** The PRD’s should-have email notifications for submission, assignment, status change, and resolution require an approved delivery provider; optional breach-escalation alerts require a campus escalation policy/provider. Neither is configured; in-app notifications are the active channel, and the UI explicitly says email/escalation are not live. Keep this open until the campus chooses and configures the external service and policy.
- [ ] **Unmeasured performance, load, and formal accessibility targets:** The PRD targets pages loading in under three seconds on average campus Wi-Fi and support for several thousand students and hundreds of concurrent issues. No campus-network timing, concurrency/load test, or formal keyboard/contrast accessibility audit has been run. The current source implements responsive layouts, labels, focus states, and privacy/input controls, but these targets remain unverified and must not be claimed as achieved.
- [ ] **Abandoned photo-object cleanup:** Managed object uploads occur before the issue database transaction so the report can retain retryable owner-bound upload tokens if submission fails. The runtime storage API does not expose deletion; a user who abandons an uploaded photo may leave an unused object in managed storage. No cleanup automation or deletion guarantee is claimed.

- [x] **Student/Administrator role selection and separated dashboards:** Before sign-in, show “CAMPUSFIX — Campus Issue Management Platform” with separate “Student Login” (“For students to report and track campus issues.”) and “Administrator Login” (“For authorities to manage and resolve campus complaints.”) choices. Provide separate role-specific login entry screens, use the existing Manus OAuth identity provider for credentials, and let that provider handle account registration/password recovery rather than adding a fake or unconfigured app-password flow. After sign-in, route according to the server-authenticated role: Students to a Student Dashboard containing Report New Issue, My Complaints, Track Complaint Status, Notifications, Profile, and Logout; Administrators to a distinct Admin Dashboard showing Total, Pending, In Progress, and Resolved complaints, with View All Complaints, Assign Complaints, Change Priority, Update Complaint Status, Manage Users, Analytics, and Logout. Students cannot access administrator pages; Administrators cannot access the Student Dashboard; user-selected role is only login intent and never grants authorization. Keep existing report/complaint functionality, Manus OAuth, database/backend, Admin/Authority/Staff workflows, CampusFix styling, responsive navigation, and correct logout. Any additional performance or formal accessibility target remains unverified unless separately measured.

- [x] **Administrator complaint review and in-progress pages:** Add Admin-only routes for `/admin/complaints` and `/admin/in-progress`, link them from the Admin workspace and mobile navigation, and retain existing assignment, status, priority, analytics, and user-management links. Show campus-wide complaint totals, current in-progress totals, each issue’s problem description, report count, status and assignee; let Admins expand an issue to review individual reporter names, filing dates, and problem descriptions using the existing role-authorized detail response. Preserve the anonymous indicator for campus-facing views, include status/search filtering, state that the list shows up to the 200 most recent records, and keep all other roles out of these Admin pages.
